# v3.2.7 · 修复：`/plugin-packages` 不认 @scope 包，带 scope 的插件此前根本下载不了

> 上一版本：`v3.2.6`。需要写进 GitHub Release 正文时直接整段粘过去。

## 本版本包含的提交（1 条）

- a629362 fix: /plugin-packages 不认 @scope 包 —— 仓库里 6 个带 scope 的插件此前根本下载不了

## 现象（生产网关实测，仓库 14 个插件、6 个带 scope）

```
GET /plugin-packages/dsh-context                     → 200
GET /plugin-packages/@lemoncat7/dsh-knowledge        → 404
GET /plugin-packages/@lemoncat7/dsh-knowledge/2.10.1 → 404
```

## 根因

下载路由按**路径段数**判 name/version，只有两个分支：`segs.length === 2` 就把第二段当版本号。
于是 `@scope/name` 被解析成 `name='@scope'`、`version='name'`；三段形式
（`@scope/name/version`）连分支都进不去，`ver` 恒为 null。

管理台侧完全看不出异常——列表、版本号、入库、默认版本全都正常。只有**客户端**从企业源
安装/更新这类插件时才会撞上，而那句「企业源拉取失败 404」并不说明问题出在包名上，
排查方向很容易被带偏到网络与仓库地址上。

影响面：所有 `@scope/` 插件（本仓库里 6 个：`@lemoncat7/dsh-knowledge`、`@xmanrui/dsh-im`、
`@deepseek-ai/dsh-base`、`@deepseek-ai/dsh-web-app`、`@deepseek-ai/dsh-experimental-*`）。
企业插件更新（客户端插件 0.9.19 的「更新到 v…」按钮）对 scoped 插件依赖这条路径，
所以升级到 3.2.7 之前，那批插件点更新会得到 404。

## 改了什么

把路径解析从路由里抽成 `core/repo-store.mjs` 的纯函数 **`parsePackagePath(rest)`**：

- 三种形态 ×（是否带 scope）全覆盖：`<name>` · `<name>/<ver>` · `<name>/-/<file>.tgz`；
- 包名过 `NAME_RE`、版本过 `VER_RE`，非法一律返回 `null`，不再把可疑字符串递到文件系统上；
- npm 风格 `<name>-<version>.tgz` **只从文件名尾部取版本号，包名以路径段为准**——
  npm 对 `@scope/name` 用的文件名是**去掉 scope** 的裸名（`dsh-knowledge-2.10.1.tgz`），
  拿它回头比对包名会把 scope 形式全部判死（这一点是本版本开发过程中自己踩的第二层坑）。

## 验证

- `node scripts/check.mjs` 66 模块语法通过；
- 新增 `test/plugin-package-path.test.mjs`，测试 5 → **8**：scoped 三种形态、
  普通包名三种形态照旧（防止为了支持 scope 而回归）、非法路径（`../`、单独 `@scope`、
  非三段版本、坏文件名）一律 `null`。
